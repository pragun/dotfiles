WezTerm × Claude Code × a tidy mind

Wez Deck

A tag-aware session picker, a three-level tree, and a relay that hands a manager agent's brain to its successor before the context window runs out. Here is what it looks like, then how it works, then how little of it we need to build first.

Chapter 1

Cmd-K for your whole life

Here is the problem in one sentence: you have nineteen tabs, fourteen of them say claude, and three of them are quietly waiting for you to answer a question they asked forty minutes ago.

The fix is one hotkey that opens one fuzzy list of every pane in every workspace. Each row carries its species, its tags, its state dot, and a context meter. Type to filter. Press Enter and you are there, workspace switch included. The mockup below is live: type #mgr, or state:need, or click a chip. Arrow keys work.

My leaning: the single most valuable key in this whole system is not the search. It is "jump to the next pane that needs me." The search is for when you know what you want. The inbox key is for when you do not, which is most of the time.
Chapter 2

Three species of session

You said it yourself: managers feel categorically different from project sessions. They are. A manager is a place you go to ask. A project session is a place you go to build. If both live in one flat list, the managers get buried under whatever you opened an hour ago.

So the tree's first level is not a folder. It is a species, and the species decides how the session is treated: how long it lives, whether it hands over, whether it appears in the inbox.

Chapter 3

Tags that survive a reboot

WezTerm can attach a value to a pane (a "user var," set with an escape sequence), and Lua can read it back. That is the live half. The catch is that it evaporates when the pane does. Restart your laptop and every tag is gone, which is exactly when you want them most.

So the truth lives in a boring JSON file, the registry, and the user vars are just a cache the tab bar reads from. Pane ids change across restarts, so the registry is keyed by something stable: the role name for managers, the repo plus worktree for projects.

// ~/.config/wezdeck/registry.json  (example)
{
  "pr-manager": {
    "kind": "manager",  "tags": ["github", "review"],
    "cwd": "~/adx/growth-detector-run-scripts",
    "gen": 3,  "live": { "pane": 14, "session": "b7e1…", "state": "needs-you", "ctx": 0.41 },
    "parked": [ { "gen": 2, "transcript": "~/.claude/projects/…/a93f.jsonl", "handover": "handover/pr-manager-g2.md" } ]
  },
  "growth-detector/live-sensor-feedback": { "kind": "project", "tags": ["lab", "sensors"] }
}

Every process in a pane inherits a WEZTERM_PANE environment variable, which means a Claude hook can find its own pane without asking anyone. That one fact is what makes the rest of this cheap.

Chapter 4

The relay: managers that never die

Now the fun part. A manager session is only useful while it remembers things, and its memory is its context window. When that fills up, Claude's built-in auto-compact kicks in and squashes the history into a summary. That is fine for a one-off task. For a pr-manager it is a bit like asking a night-shift nurse to hand over to the morning shift by describing the ward from memory, with a blindfold on.

The relay does it properly. At 80% the manager writes its own handover note while it still has 20% of its wits, a fresh session starts and reads it, and the old one stays in the tree, parked, with its full transcript intact. Think of it as keeping the retired expert in the next office.

  1. Measure after every turn.

    Claude Code hooks receive the session id and the path of the transcript file. On each Stop, a small script reads the last assistant message's token usage (input plus cache reads plus cache writes) and divides by the model's window. That is your context percentage. No daemon, no polling.

  2. At 80% and idle, ask for the handover.

    Stop means the agent has finished its turn, so it is safe to type at it. The script runs wezterm cli send-text --pane-id $WEZTERM_PANE with a prompt: write a handover note covering open threads, standing instructions, what you are waiting on, and where the bodies are buried.

  3. Spawn the successor next door.

    When the note exists, the next Stop spawns a new tab with wezterm cli spawn, same cwd, same tags, generation plus one, starting with: "You are pr-manager g4. Read the handover, check it against the real world, then report READY."

  4. Park the elder.

    The old pane stays open and is relabelled parked. Its transcript path goes in the handover note, so the new manager can grep the old one for details the summary dropped. You can also just walk over and ask it.

  5. The name follows the living.

    "pr-manager" in the picker and in the inbox always resolves to the live generation. Parked ones only show when you ask for lineage.

Guard rails, because a loop that spawns agents is a loop that can spawn too many

One in flightA manager can have only one handover running. No successor until the note exists and is non-empty.
Cool-downIf a fresh generation is already above 50% within minutes of birth, stop and flag it. Something is wrong with the note.
Visible logEvery spawn lands in an event list in the tree, and the status strip shows "1 near handover" before it happens.
Per-species policyManagers auto-relay. Projects only get a nudge. Scratch is never touched.
My leaning: the "meta agent that watches other agents" should start as a plain script, not another Claude. Reading a token count and typing a prompt needs no intelligence. Save the LLM for later, when you want a chief-of-staff session that reads everyone's transcripts and answers "what is the team doing and what is stuck."

Things I would check before trusting this

Three assumptions to verify in an hour of poking, before any real building: that the hook payload's transcript path reliably yields a usable token count on your Claude Code version; that send-text lands cleanly in Claude's input box when the pane is idle (paste mode versus raw, and the final Enter); and what window size your managers actually run with, since 80% of 200k and 80% of 1M are very different stories.

Chapter 6

Pulling the threads together

Strip away the mockups and this is three small ideas stacked. A registry gives every pane a stable identity and some tags. Hooks keep that registry honest about what each agent is doing and how full its head is. A picker and a status strip turn all of it into something you can read at a glance and steer with one key. The relay is just a rule on top: when a manager's head is 80% full, give it a pen and a notepad and introduce it to its replacement.

The nice part is that nothing here fights WezTerm. It is all Lua, wezterm cli, and hooks you already know how to write. The risky part is the relay's two soft spots (token maths and typing into a live pane), and both can be checked in an hour before anything else gets built.

What I need from you to start slice 0: where your wezterm.lua lives, whether the three species above match how you think about your sessions (or whether "manager" needs a sibling, like a "watcher"), and which window size your managers run with. If that all looks right, say go and I will build slices 0 and 1 first, then spike the relay to see whether the assumptions hold.
